# BepulMed AI 2.8 — DMED и защита данных

## DMED (по официальной спецификации DHP: FHIR + OAuth 2.0)
- Модуль подключения: вход через sso.dhp.uz (authorization code + PKCE S256, проверка state, срок 10 мин),
  только чтение FHIR R5/R4: пациент, поликлиника прикрепления, электронные рецепты, предстоящие записи.
- Рецепты сверяются с перечнем бесплатных лекарств (приказ МЗ № 18) — отметка «бесплатно по программе».
- Экран согласия перед входом; токен и данные только в памяти; «Выйти» удаляет сразу.
- Android: возврат `uz.bepulmed.app:/oauth2redirect`, вход в системном браузере, HTTP-мост к *.dhp.uz.
- iOS: ASWebAuthenticationSession (эфемерная сессия), URLSession.ephemeral.
- **Выключено, пока Uzinfocom не выдаст client_id** (`VITE_DMED_CLIENT_ID`). Без него в DMED не уходит ни одного запроса.
- Голос: «мои рецепты», «открой DMED» → экран DMED.

## Защита данных
- Content-Security-Policy в сборке, no-referrer; заголовки статики (`_headers`) и API (HSTS, no-referrer, frame-ancestors).
- Экран «🔒 Защита данных»: действующие меры на телефоне и флаги сервера; удаление сохранённых талонов, отзыв согласия на сетевое распознавание.
- Документы `SECURITY_AND_COMPLIANCE_RU.md` и `DMED_INTEGRATION_RU.md` обновлены (исправлены сломанные `\n`).

## Проверено
- web 113 тестов (в т.ч. 16 по DMED: SHA-256 против node:crypto, вектор RFC 7636, state/просрочка/повтор,
  обмен кода, R5/R4, бесплатные лекарства, запрет посторонних хостов), worker 127, tsc.
- e2e с поддельными SSO/FHIR: Android-режим (мост), веб-режим (переход и возврат с ?code), подмена state отклоняется,
  токен не попадает в хранилище, выход очищает; обычная сборка — «не подключено», 0 запросов к DMED.
- OCR и карта при включённой CSP — без нарушений. Повторно: офлайн-сценарий 2.7 и iOS-имитация.
- APK 2.8 собран и подписан. iOS: синтаксис Swift проверен, компиляция — только на Mac/GitHub Actions.

## Не проверено
- С настоящим DMED (нужна регистрация приложения). Точные адреса authorize/token и scopes уточнить у Uzinfocom.
